🟠 Chapter 1 — Introduction
⚡ 中斷機制（Interrupt）每年必考

關鍵名詞：

  • Interrupt-request line：CPU 在每條指令後都會檢查此線
  • Interrupt vector：儲存各中斷服務程式位址的表格（IVT）
  • Trap（軟體中斷）：由軟體錯誤或 system call 觸發
  • Interrupt handler：處理特定中斷的程式碼
⚠️ 考題必答

Interrupt Vector 的好處：

直接查表找到對應的 interrupt-specific handler，不需逐一搜尋所有 handlers，加速中斷處理速度

⚡ Interrupt-based vs Busy-waiting（中斷 vs 輪詢）

Busy-waiting（輪詢）：

CPU 持續循環檢查設備是否就緒，大量浪費 CPU 時間，CPU 長時間閒置

Interrupt-based（中斷驅動）：

CPU 繼續執行其他工作，等設備完成才發中斷，CPU 使用率高

完整流程：

  1. 使用者程式呼叫 API 函數（如 read()）
  2. API 函數觸發 software interrupt（trap），CPU 切換到 kernel mode（dual-mode）
  3. 將 system call number（index） 放入 EAX 暫存器
  4. CPU 使用 index 查詢 table of code pointer，找到 kernel 函數位址
  5. 執行對應的 kernel 服務
  6. 完成後 CPU 切回 user mode，回傳結果
為何程式設計師偏好 API？（每年必考）
  1. Portability（可攜性）：API 在不同作業系統上提供一致介面
  2. Simplicity（簡便性）：API 比直接呼叫 system call 簡單，不需了解底層細節
💻 CLI 兩種實作方式（2015考）
方式一：內建命令

指令程式碼內建在直譯器中

✅ 優點：執行速度快

❌ 缺點：直譯器體積大；少用指令浪費記憶體；新增指令需修改直譯器

方式二：系統程式（UNIX 方式）

直譯器不含指令碼，搜尋 PATH 找到程式後載入執行

✅ 優點：直譯器體積小；可輕易新增指令

❌ 缺點：執行指令需搜尋和載入，速度較慢

🏗️ OS 結構比較
架構描述✅ 優點❌ 缺點
Layered（分層） OS 分為 N 層，每層只呼叫下一層 易於除錯（逐層驗證） 難定義各層；效能差（多層開銷）
Microkernel（微核心） 只保留最基本服務，其他移到 user space，用 message passing 溝通 可靠、可移植、安全 效能開銷大（user/kernel 間頻繁 message passing）
Modules（模組化） ⭐現代主流 Core kernel + 可動態載入的核心模組（LKM） 彈性高、效率高（不需 message passing）；模組間可直接溝通 -
Modular 優於 Layered 和 Microkernel（2013 考）

• 比 Layered：模組間可直接溝通，不需穿越多層，效率更高

• 比 Microkernel：模組在 kernel space 執行，不需 message passing 的開銷

🍴 Fork / Exec / Wait / Exit
pid_t pid = fork(); // 子行程回傳 0 // 父行程回傳 子PID(>0) // 失敗回傳 -1 if (pid == 0) { // 子行程 execlp("ls", "ls", NULL); } else { // 父行程 wait(NULL); // 等子行程 printf("done\n"); }
⚠️ 重要觀念
  • fork() 後父子行程有各自獨立的位址空間副本
  • 修改一方的變數完全不影響另一方
  • 全域變數也是各自獨立的
移除 wait(NULL) 的後果？

父子並行執行，輸出順序不定；子行程結束後無人收拾 → Zombie process（殭屍行程）

🔬 2016 考題 fork() 輸出分析 必考題型
int value = 5; // 全域變數 int main() { pid_t pid = fork(); if (pid > 0) { // 父行程 value += 15; wait(NULL); printf("value=%d\n", value); } else if (pid == 0) { // 子行程 value += 5; printf("value=%d\n", value); } }
輸出結果：

子行程先印： value = 10 （5 + 5 = 10）

父行程後印： value = 20 （5 + 15 = 20）

父行程等 wait 完成後才印，故父後於子

移除 wait(NULL) 後？

輸出順序不確定（non-deterministic），子行程結束後可能成為 zombie process

🧠 Shared Memory API（System V） 每年必考
// 1. 建立/取得共享記憶體 int segment_id = shmget(IPC_PRIVATE, sh_size, S_IRUSR | S_IWUSR); // 2. 附加（attach）到行程位址空間 int *shared_memory = (int *) shmat(segment_id, NULL, 0); // 3. 使用：像普通指標一樣操作 *shared_memory = 0; // 初始化 // 4. 分離（detach） shmdt(shared_memory); // 5. 移除 shmctl(segment_id, IPC_RMID, NULL);

計算 2x+3y-5 的標準解答（2015考）：

for (i = 2; i > 0; i--) { // 建立 2 個子行程 pid = fork(); if (pid == 0) { // 子行程 if (i == 2) *shared_memory += 2 * x; // 計算 2x if (i == 1) *shared_memory += 3 * y; // 計算 3y shmdt(shared_memory); exit(0); } else { wait(NULL); } // 父行程等待 } *shared_memory -= 5; // 計算 -5 printf("result=%d\n", *shared_memory); shmdt(shared_memory); shmctl(segment_id, IPC_RMID, NULL);

🧵 Thread 概念：擁有 vs 共享
🔒 每個 Thread 自己擁有
  • Thread ID

  • Register set（暫存器集合）

  • 程式碼（code / text section）
  • 資料（data section）

Thread 比 Process 便宜的原因（2015, 2016 考）

建立 Thread 不需複製整個位址空間（text/data/heap），只需建立 PC/registers/stack。在 Solaris 中，Thread 建立比 Process 快約 30 倍。

⚖️ 執行緒模型比較 每年必考
Many-to-One（多對一）

多個 user thread → 一個 kernel thread

✅ Thread 管理在 user space，效率高，不需 system call

❌ 一個 thread 做 blocking call → 整個行程阻塞；無法在多處理器平行執行

One-to-One（一對一）⭐ Linux / Windows

每個 user thread → 一個 kernel thread

✅ 一個 thread 阻塞不影響其他；可在多處理器真正平行執行

❌ 建立 user thread 就要建立 kernel thread，overhead 大；數量可能受限

Many-to-Many（多對多）

多個 user thread ↔ 多個 kernel thread（kernel thread 數 ≤ user thread 數）

✅ 兼具兩者優點；可建立足夠多 user threads；一個阻塞不影響其他

🔔 Scheduler Activations（排程器激活）2011-2014 常考
解決什麼問題？

Many-to-Many 模型中，若 user thread 做 blocking system call，kernel 會阻塞整個行程。Scheduler Activations 讓 kernel 能即時通知 thread library，讓 library 調度其他 thread。

LWP（Lightweight Process）：kernel 與 thread library 之間的虛擬處理器，thread library 在 LWP 上排程 user threads。

運作流程（考試必答步驟）：

  1. User thread 準備做 blocking system call
  2. Kernel 偵測到即將阻塞，透過 upcall（向上呼叫）通知 thread library
  3. Thread library 的 upcall handler 儲存被阻塞 thread 的狀態
  4. Thread library 在可用的 LWP 上排程另一個可執行的 user thread
  5. Blocking call 完成後，kernel 再次 upcall 通知 thread library
  6. Thread library 將原 thread 標記為 ready，擇機重新排程
🔴 Chapter 5 — CPU Scheduling
📐 排程標準（Scheduling Criteria）

最大化：

  • CPU utilization：CPU 使用率
  • Throughput：單位時間完成的行程數

最小化：

  • Turnaround time：從提交到完成的時間
  • Waiting time：在 ready queue 等待的總時間
  • Response time：從提交到第一個回應的時間
🔁 可搶占 vs 不可搶占排程 2014 考
情況排程決策類型
① running → waiting（如 I/O request）必須選新的行程非搶占
② running → ready（如 interrupt 發生）可選繼續或切換可搶占
③ waiting → ready（如 I/O 完成）可選切換給新 ready 的可搶占
④ 行程 terminates（終止）必須選新的行程非搶占

情況 1 和 4 是非搶占的必然情況；情況 2 和 3 是可搶占排程的關鍵點

📊 排程演算法比較
演算法描述優點缺點
FCFS先來先服務，非搶占簡單Convoy Effect（短行程卡在長行程後）
SJF選 CPU burst 最短的平均等待時間最短（optimal）難以預知下次 burst 長度

規則

Priority Scheduling 的飢餓問題

解法：Aging（老化）— 隨著等待時間增加，逐漸提高行程的優先權，確保低優先權行程最終會被執行

🔑 三個核心名詞

LWP（Lightweight Process）

Kernel 和 thread library 之間的虛擬處理器。Thread library 在 LWP 上排程 user threads；LWP 背後由 kernel thread 驅動。

Upcall（向上呼叫）

Kernel 主動通知 thread library 的機制（由下往上）。當 blocking event 發生或完成時，kernel 透過 upcall 讓 thread library 做出回應。

Upcall Handler

Thread library 中負責接收並處理 upcall 的函數。收到 upcall 後，儲存被阻塞 thread 的狀態，並立即排程另一個 ready thread。

📝 考試必答步驟（8步）
  1. User thread T1 準備做 blocking system call
  2. Kernel 偵測到 T1 即將阻塞
  3. Kernel 透過 upcall #1 通知 thread library
  4. Upcall handler 儲存 T1 的狀態
  5. Thread library 在 LWP 上排程另一個 user thread（T2）
  6. T2 開始執行，T1 等待 I/O 完成
  7. I/O 完成，Kernel 透過 upcall #2 通知 thread library
  8. Thread library 將 T1 標記為 ready，擇機重新排程
