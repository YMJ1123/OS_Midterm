Chapter 1 — Introduction
Interrupt Mechanism Must-Know

Key Terms:

  • Interrupt-request line: CPU checks this line after every instruction
  • Interrupt vector: Table storing addresses of interrupt service routines (IVT)
  • Trap (software interrupt): Triggered by software errors or system calls
  • Interrupt handler: Code that handles a specific interrupt
Exam Must-Answer

Benefits of Interrupt Vector:

Directly look up the table to find the corresponding interrupt-specific handler, no need to search through all handlers one by one, speeding up interrupt processing

Interrupt-based vs Busy-waiting (Polling)

Busy-waiting (Polling):

CPU continuously loops checking if the device is ready, wastes a lot of CPU time, CPU remains idle for long periods

Interrupt-based:

CPU continues executing other work, device sends interrupt only when done, high CPU utilization

Dual-Mode Operation
Kernel Mode
mode bit = 0
Can execute all instructions
User Mode
mode bit = 1

How does it protect the OS?

Privileged instructions can only execute in kernel mode. If user mode attempts to execute them → hardware trap → OS handles it, preventing malicious/erroneous programs from damaging the system

Chapter 2 — System Structures
System Call via API Must-Know
4 Keywords You MUST Mention on the Exam
Software Interrupt
Mechanism that triggers kernel intervention
Dual-mode
User mode → Kernel mode switch
System Call Number (Index)
Placed in EAX register
Table of Code Pointer
Look up table to find system call address

Complete Flow:

  1. User program calls an API function (e.g., read())
  2. API function triggers software interrupt (trap), CPU switches to kernel mode (dual-mode)
  3. Places system call number (index) into EAX register
  4. CPU uses index to look up table of code pointer, finds kernel function address
  5. Executes the corresponding kernel service
  6. After completion, CPU switches back to user mode, returns result
Why do programmers prefer API? (Must-Know)
  1. Portability: API provides a consistent interface across different operating systems
  2. Simplicity: API is simpler than directly calling system calls, no need to understand low-level details
CLI Two Implementation Methods (2015 Exam)
Method 1: Built-in Commands

Command code is built into the interpreter

Pros: Fast execution

Cons: Interpreter is large; rarely-used commands waste memory; adding commands requires modifying interpreter

Method 2: System Programs (UNIX approach)

Interpreter contains no command code, searches PATH to find and load programs

Pros: Interpreter is small; easy to add new commands

Cons: Executing commands requires searching and loading, slower

Fork / Exec / Wait / Exit
pid_t pid = fork(); // Child returns 0 // Parent returns child PID (>0) // Failure returns -1 if (pid == 0) { // Child process execlp("ls", "ls", NULL); } else { // Parent process wait(NULL); // Wait for child printf("done\n"); }
Important Concepts
  • After fork(), parent and child have separate copies of the address space
  • Modifying variables in one does not affect the other
  • Global variables are also independent copies
What happens if we remove wait(NULL)?

Parent and child execute concurrently, output order is non-deterministic; after child finishes, no one collects its status → Zombie process

2016 Exam: fork() Output Analysis Must-Know
int value = 5; // global variable int main() { pid_t pid = fork(); if (pid > 0) { // Parent value += 15; wait(NULL); printf("value=%d\n", value); } else if (pid == 0) { // Child value += 5; printf("value=%d\n", value); } }
Output:

Child prints first: value = 10 (5 + 5 = 10)

Parent prints second: value = 20 (5 + 15 = 20)

Parent waits for wait() to complete before printing, so parent prints after child

What if wait(NULL) is removed?

Output order is non-deterministic, child process may become a zombie process after termination

Why is Thread Creation Cheaper than Process Creation? (2015, 2016 Exam)

Creating a thread does not need to duplicate the entire address space (text/data/heap), only needs to create PC/registers/stack. In Solaris, thread creation is about 30 times faster than process creation.

Thread Model Comparison Must-Know
Many-to-One

Multiple user threads → one kernel thread

Pros: Thread management in user space, efficient, no system call needed

Cons: One thread making a blocking call → entire process blocks; cannot run in parallel on multiprocessors

One-to-One (Linux / Windows)

Each user thread → one kernel thread

Pros: One thread blocking doesn't affect others; can truly run in parallel on multiprocessors

Cons: Creating a user thread requires creating a kernel thread, high overhead; count may be limited

Many-to-Many

Multiple user threads ↔ multiple kernel threads (kernel threads ≤ user threads)

Pros: Combines advantages of both; can create sufficient user threads; one blocking doesn't affect others

Scheduler Activations 2011-2014 Frequent
What problem does it solve?

In the Many-to-Many model, if a user thread makes a blocking system call, the kernel blocks the entire process. Scheduler Activations allow the kernel to immediately notify the thread library, letting the library schedule another thread.

LWP (Lightweight Process): A virtual processor between the kernel and thread library. The thread library schedules user threads on LWPs.

Operation Flow (Exam Must-Answer Steps):

  1. User thread is about to make a blocking system call
  2. Kernel detects the upcoming block, notifies thread library via upcall
  3. Thread library's upcall handler saves the blocked thread's state
  4. Thread library schedules another runnable user thread on an available LWP
  5. When the blocking call completes, kernel sends another upcall to the thread library
  6. Thread library marks the original thread as ready, reschedules it when appropriate
Chapter 5 — CPU Scheduling
Scheduling Criteria

Maximize:

  • CPU utilization: Keep the CPU as busy as possible
  • Throughput: Number of processes completed per time unit

Minimize:

  • Turnaround time: Time from submission to completion
  • Waiting time: Total time waiting in ready queue
  • Response time: Time from submission to first response
Preemptive vs Non-preemptive Scheduling 2014 Exam
CaseScheduling DecisionType
1. running → waiting (e.g., I/O request)Must select a new processNon-preemptive
2. running → ready (e.g., interrupt occurs)May continue or switchPreemptive
3. waiting → ready (e.g., I/O completes)May switch to newly ready processPreemptive
4. Process terminatesMust select a new processNon-preemptive

Cases 1 and 4 are inherently non-preemptive; cases 2 and 3 are the key points for preemptive scheduling

AlgorithmDescriptionProsCons

Multilevel Feedback Queue 2014, 2015 Must-Know

Three-Level Structure:

Q2 (Highest Priority)
Round-Robin, time quantum = 4 ms
New processes enter here
Q1 (Medium Priority)
Round-Robin, time quantum = 6 ms
Demoted from Q2 after timeout
Q0 (Lowest Priority)
FCFS
Demoted from Q1 after timeout
Rules
  • New processes enter Q2 (highest priority level)
  • If completed within quantum → leave CPU
  • If timeout (preempted) → demoted to next level
  • Higher priority level processes preempt lower level processes
Waiting Time Calculation

Waiting time = Completion time - Arrival time - Total CPU burst

(Waiting time = time spent in ready queue, excluding I/O time)

Starvation in Priority Scheduling

Solution: Aging — gradually increase the priority of a process as its waiting time increases, ensuring low-priority processes eventually get executed

Three Core Concepts

LWP (Lightweight Process)

A virtual processor between the kernel and thread library. The thread library schedules user threads on LWPs; each LWP is backed by a kernel thread.

Upcall

A mechanism for the kernel to proactively notify the thread library (bottom-up). When a blocking event occurs or completes, the kernel uses an upcall so the thread library can respond.

Upcall Handler

A function in the thread library that receives and processes upcalls. Upon receiving an upcall, it saves the blocked thread's state and immediately schedules another ready thread.

Exam Must-Answer Steps (8 Steps)
  1. User thread T1 is about to make a blocking system call
  2. Kernel detects that T1 is about to block
  3. Kernel notifies thread library via upcall #1
  4. Upcall handler saves T1's state
  5. Thread library schedules another user thread (T2) on the LWP
  6. T2 begins executing, T1 waits for I/O to complete
  7. I/O completes, kernel notifies thread library via upcall #2
  8. Thread library marks T1 as ready, reschedules when appropriate
